# Вынос корпуса в отдельный репозиторий

Статус: шаги 1–2 выполнены 2026-09-24 (`fa3b8d0`, `39a8e35`). Шаг 3 — перевод `rodos-assistant` —
**ждёт** слияния его PR #19 и #20 и разрешения владельца: их код читает пути `corpus/` напрямую,
и перенос прошёл бы ровно по линии будущего конфликта. Порядок согласован с сессией, которая эти
PR ведёт.

## 1. Зачем

Один вымышленный мир, два приложения. «Родос-Ассистент» отвечает по документам ГК «Родос-Деталь»;
«Родос-Агент» действует в её системах по её же регламентам. Если мир скопировать, копии разойдутся —
и вместо платформы получатся два стенда, которые случайно похожи.

Побочная выгода: корпус становится самостоятельным артефактом. Синтетический корпус предприятия на
372 документа, побайтово воспроизводимый, с линтером фиктивности реквизитов и разбором происхождения
— это archetype «RAG data pipeline» из разбора рынка, и он читается сам по себе.

## 2. Что переезжает

| Из `rodos-assistant` | В `rodos-corpus` |
|---|---|
| `world/` (13 файлов: площадки, цеха, люди, роли, детали, материалы, оборудование, продукция, контрагенты, договоры, ЦФО, календарь, системы) | `rodos_corpus/world/` |
| `corpus/source/`, `corpus/rendered/`, `corpus/cards/` | `rodos_corpus/corpus/` |
| `corpus/PROVENANCE.md` | туда же |
| `src/rodos/corpus/` (`build`, `generators/`, `lint`, `render`, `source`, `world`) | `src/rodos_corpus/` |
| `assets/fonts/` (DejaVu + LICENSE) | `rodos_corpus/assets/fonts/` |
| гейт воспроизводимости из CI | CI корпуса |
| ADR-0008 (происхождение), ADR-0011 (побайтовая воспроизводимость) | `docs/adr/` корпуса |
| тесты корпуса (`test_render`, линтер, генераторы) | тесты корпуса |

Остаётся в ассистенте: `spaces/*.yaml`, `routing.yaml`, `evals/golden/`, `docflow.yaml`, `migrations/`
— это его прочтение мира, а не сам мир.

Спорная граница, решённая явно: поля `spaces` и `confidentiality` в карточке документа **остаются в
корпусе**. Это свойства документа на предприятии («договор относится к финансам и производству,
гриф ДСП»), а не настройка конкретного поисковика. Как их интерпретировать — дело приложения.

## 3. Что появляется нового

- **`stream/`** — поток входящих событий для «Родос-Агента»: письма контрагентов с запросами цен,
  присланные проекты договоров, каждый с конвертом (`from`, `channel`, `received_at`). Статический
  корпус — это то, что у предприятия уже есть; поток — это то, что к нему приходит. Генератор
  `generators/inbound.py`, те же правила фиктивности.
- **`MANIFEST.json`** — `{doc_id: sha256}` по всем документам плюс версия корпуса. Даёт две вещи:
  потребитель может проверить целостность, а прогон оценки — записать, на какой версии корпуса он
  получен. Это ровно та причина, по которой корпус вообще делали воспроизводимым (ADR-0011).
- **Публичный API пакета** — вместо `Path(__file__).parents[3]`:

```python
from rodos_corpus import World, load_all, corpus_root, world_root, stream_root, manifest

World.load()            # модель мира
load_all()              # SourceDoc по всему корпусу
corpus_root()           # каталог отрендеренных файлов (importlib.resources)
manifest()              # {doc_id: sha256} + version
```

## 4. Как пакет попадает в приложения

**ВЫБОР: зависимость git с тегом, приколоченная в `uv.lock`.**

```toml
[project]
dependencies = ["rodos-corpus"]

[tool.uv.sources]
rodos-corpus = { git = "https://github.com/alexten/rodos-corpus", tag = "v1.0.0" }
```

`uv.lock` записывает точный коммит, так что сборка остаётся воспроизводимой. Данные (`world/`,
`corpus/`, `stream/`, `assets/`) едут внутри пакета и читаются через `importlib.resources`.

Отвергнуто: **submodule** — `git clone` без `--recursive` даёт пустой каталог, а обещание ADR-0008
«работает сразу после клонирования» слишком дорого стоило, чтобы его ломать. **Вендоринг копии** —
20 МБ на репозиторий и ручная синхронизация, то есть тот самый расход, ради устранения которого всё
затевается.

Что при этом не нарушается из ADR-0008: ключи API по-прежнему не нужны, генерация на лету
по-прежнему не происходит. `uv sync` и так ходит в сеть за langgraph — ещё одна зависимость ничего не
меняет.

## 5. Порядок работ

Первые два шага — в репозитории корпуса, третий трогает ассистента и требует чистого дерева.

1. **Создать `rodos-corpus`.** ✅ Сделано. Перенести файлы с историей (`git filter-repo --path`, чтобы коммиты по
   корпусу не потерялись), собрать пакет, перенести тесты, поднять CI с гейтом
   `generate && render && git diff --exit-code`, написать README с баннером «предприятие вымышлено» и
   `PROVENANCE.md`. Тег `v1.0.0`.
2. **Проверить исполнением, а не чтением.** ✅ Сделано: полная пересборка (`generate` + `render`)
   всех 372 документов в новой раскладке не меняет ни байта, а CI прогнал тот же гейт на чужой
   машине. Набор файлов и его хеш совпадают с исходным репозиторием. В пустом каталоге: `uv add`, затем `python -c "from
   rodos_corpus import load_all; print(len(load_all()))"` → 372. Отрендеренные файлы читаются из
   установленного пакета, а не из рабочей копии.
3. **Перевести `rodos-assistant`.** ⏳ Оба PR влиты (#20 — `ef23ef2`, #19 — main на `3dbce70`,
   CI зелёный). **Осталось единственное условие — согласие оператора**; работа непустая и трогает
   репозиторий, который он ведёт, поэтому по своей инициативе я её не начинаю.

   План сверен с новым main (чтение мелкой копии, рабочую копию оператора не трогал): **API пакета
   покрывает и то, что добавил #19**, ничего дописывать не нужно.

   | Что делает код на main | Чем становится |
   |---|---|
   | `(root / "corpus" / "cards").glob("*.yaml")` — `evals/extraction.py:101`, `evals/routing.py:83` | `cards_root().glob("*.yaml")` |
   | `root / card["rendered"]` — `evals/extraction.py:110`, `evals/routing.py:134` | `rendered_path(card)` |
   | `SEEDED = Path("corpus") / "rendered"` как корень посева — `evals/routing.py:59` | `rendered_root()` |

   **`seeded_folder()` — место, требующее внимания при переносе.** Она (`evals/routing.py:141`, из
   issue #18) считает подпапку так: `Path(card["rendered"]).relative_to(SEEDED).parts`, то есть
   операцией **над строкой карточки**, а не над файловой системой. В пакете строка сохранена дословно
   (`corpus/rendered/<пространство>/<файл>` — проверено: у всех карточек корпуса префикс ровно такой),
   поэтому `seeded_folder()` продолжает работать **без единой правки**.

   Три исхода, проверены запуском:

   | Что подставили | Что будет |
   |---|---|
   | строка карточки против относительного `SEEDED` (как сейчас) | `('sales', 'a.pdf')` — верно |
   | абсолютный `rendered_path(card)` против относительного `SEEDED` | `ValueError: … is not in the subpath of 'corpus/rendered'` — **падает громко на первом же документе** |
   | абсолютный путь против `rendered_root()` | `('sales', 'a.pdf')` — тоже верно |

   То есть половинчатая замена не тихая, а шумная: `--as-seeded` упадёт сразу, и это хороший исход.
   **Тихий риск лежит в другом месте** — в раскладке под корнем. Если под `rendered_root()` окажется
   не `<пространство>/<файл>`, `parts[0]` вернёт не то имя, и не упадёт ничего. Поэтому «первый
   подкаталог под `rendered_root()` — ключ пространства» и записано в API как инвариант, который менять
   нельзя: на нём держится маршрутизация у потребителя. Правило переноса остаётся: `card["rendered"]`
   как строка остаётся строкой, абсолютные пути — только там, где открывается файл; а если менять, то
   обе стороны `relative_to` сразу. Удалить
   перенесённое, добавить зависимость, заменить вызовы на API пакета, перенести гейт
   воспроизводимости из его CI, добавить дешёвую проверку `MANIFEST.json`, написать ADR о выносе (он
   уточняет ADR-0008, а не отменяет его). Зелёный `make check` и зелёный CI — условие приёмки; корпус
   после этого обязан индексироваться в стенд без изменений.

   **Три правки конфигурации, которые входят в этот же диф.** Корпус с версии 1.2.0 несёт две новые
   роли, и это меняет то, что ассистент читает из каталога ролей:

   - `yuriskonsult` **добавить** в `roles.ask` пространств `finance` и `sales`. Роль без доступа ни к
     одному пространству принимается как `X-Rodos-Role` (A-73 берёт ключи дословно) и не может
     спросить ничего, а `FIN-REGL-DOGOVOR` п. 3.1.1 ставит юридическую проверку первым этапом
     согласования договора — юрисконсульт, не читающий финансовое пространство, этот этап не
     проходит. В `roles.dsp` **не** добавлять.
   - `nachalnik_pds` — доступа не давать. Агент только ставит ему задачу на подтверждение срока;
     читать документы ему для этого не нужно.
   - `agent_service` **завести** и добавить в `roles.dsp` пространства `sales`. Без этого путь по
     умолчанию у [rodos-agent] не работает физически: `SALES-REGL-SKIDKI` имеет гриф `dsp`, а
     `roles.dsp` там — `[kom_direktor, gen_direktor]`, то есть агент не получит регламент, по которому
     считает скидку. Следствие, которое надо принять осознанно: агент читает **на уровне
     коммерческого директора**, а безопасность даёт фильтр раскрытия, а не урезанные права чтения.

   Проверено чтением кода: `spaces.py:207` проверяет только направление «пространство → роль», то есть
   роль, которую не упоминает ни одно пространство, — не нарушение, и `spaces validate` от появления
   двух новых ролей не краснеет. Жёсткого числа ролей в `src/` и `tests/` нет. То есть это решения,
   а не поломка.
4. **Только потом** — `rodos-agent`. Спецификации при этом уже пишутся: агент берёт корпус из
   пакета с первого дня и переводом ассистента не заблокирован.
